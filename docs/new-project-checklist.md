# 新项目使用清单

这个仓库更适合作为 GitHub Template 使用，而不是依赖一次性的初始化脚本。创建新仓库后按清单逐项确认，可以保留透明、可审查的变更记录，也不会让脚本擅自重写业务代码。

## 创建仓库

1. 在 GitHub 仓库设置中启用 **Template repository**。
2. 新项目优先点击 **Use this template** 创建独立仓库，避免继承模板仓库的提交历史。
3. 克隆新仓库，运行 `pnpm install`。
4. 复制 `.env.example` 为 `.env`，更换 `BETTER_AUTH_SECRET`、管理员邮箱和强密码。

## 品牌与配置

- 修改 `package.json` 的包名和版本。
- 修改 `src/config/app-config.ts` 中的应用名、标题、描述和版权信息。
- 替换 `src/app/favicon.ico`、README 标题和项目说明。
- 检查端口、`BETTER_AUTH_URL`、数据库路径以及部署环境变量。

应用名称集中在 `APP_CONFIG`，认证配置也读取这里的名称。新增全局品牌信息时继续放在该配置中，避免散落硬编码。

## 数据与权限

- 运行 `pnpm setup` 创建空数据库并初始化唯一管理员。
- 确认普通用户、管理员和项目所有权规则是否符合新业务。
- 不需要示例项目时保持数据库为空；不要提交 `.env`、SQLite、WAL 或 SHM 文件。
- 上线或迁移前运行 `pnpm db:backup`，并实际演练一次恢复。

## 按业务裁剪

- 将 `project` 示例域改名或替换为真实业务域。
- 更新工作区导航、设置项和审计动作。
- 删除不用的页面和依赖时，同时更新测试与产品文档。
- 如果引入邮件、OAuth、对象存储、队列或多租户，重新评审环境变量、授权边界和限流策略。

## 交付前验证

```bash
pnpm check
pnpm typecheck
pnpm test:unit
pnpm test:e2e
pnpm build
```

GitHub Actions 会在 `main` 推送和 Pull Request 上执行静态检查、类型检查、单元测试和构建。耗时较长的 E2E 仅在推送到 `main` 或手动触发工作流时运行。首次创建模板仓库时，在 GitHub 设置中将基础 CI 设为分支保护的必需检查。

## 何时再考虑初始化脚本

先用模板完成 2–3 个真实项目。只有当多个项目反复出现同一批、可确定且无业务判断的机械修改时，再增加交互式脚本；例如统一改包名、显示名称和端口。涉及权限模型、业务域、数据结构或删除功能的选择仍应人工评审，不应交给初始化脚本默认决定。
